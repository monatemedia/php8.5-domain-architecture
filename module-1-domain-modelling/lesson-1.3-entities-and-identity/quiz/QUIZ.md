<summary><strong>Answer key</strong></summary>

**Q1 — B.** "This one, specifically." A vehicle: yes. Five hundred euros: no.

**Q2 — B.** Two vehicles. Identity is what distinguishes them, and attributes cannot.

**Q3 — B.** Identity only. Anything else means an edited entity stops being itself.

**Q4 — C.** It changes. A vehicle can be re-registered and it is the same vehicle, so every job card,
report and audit row keyed on the old value is now orphaned by an ordinary business event.

**Q5 — B.** If the key changed, would the business say it is a different thing? For a registration:
no. So it fails.

**Q6 — B.** The nulls. And they spread — every constructor grows a `?int`, every `equals()` grows a
null branch, and every consumer must handle an object that does not know who it is. That is Lesson
0.2's shared-model tell arriving on your domain model. (A is not the point: surrogate integers
perform *better* than UUIDs.)

**Q7 — B.** Rule 1, in the most inconvenient place — it hits every test you will ever write.

**Q8 — B.** Time-ordered, so inserts land at the end of the index rather than in random positions.

**Q9 — B.** A rule about a sequence. Holding a single reading, there is nothing to compare it to.

**Q10 — B.** `readonly` forbids writes after construction even from inside, so the entity cannot
express its own lifecycle.

**Q11 — FALSE.** It is a fact about what the context *does* with it. A vehicle is an entity to the
workshop and a value (a fitment key) to the parts desk, and neither is wrong. This is Lesson 0.2 and
Lesson 1.3 being the same subject from two angles.

**Q12 — TRUE.** "May never decrease" is not "must always increase". A vehicle in for two jobs on the
same day has not moved.

**Q13 — TRUE**, and it is built anyway. The justification is stated rather than assumed: identifiers
are passed more than any other value, and the bug a typed identifier prevents is silent — the wrong
string in the right parameter attaches the wrong record without throwing. Being able to say *why* an
exception is justified is the skill; ignoring the rule silently is not.

**Q14 — FALSE.** Withers are for value objects, which are replaced wholesale. An entity has
continuous identity and changes in place — a `withOdometer()` returns a second object claiming to be
the same vehicle, and then you have to decide which one is real.

**Q15 — FALSE.** It undoes Lesson 1.2 one caller at a time. The first consumer compares the returned
string with `===` against something un-normalised, and the four-spellings bug is back — in a place
nobody will look, because the value object still exists and appears to be doing its job.

**Q16** The obvious answer is `Vehicle`: an entity to the workshop (a history, a bay, faults — *that*
one), a value to the parts desk (a fitment key: two vehicles with the same engine code, year and
trim are interchangeable). Also good: a *bank note* is a value to you and an entity to the mint,
which tracks serial numbers. Or a *seat* on a plane: a value when you are counting capacity, an
entity when it is 14A and it is yours.

**Q17** It is asking whether the *workshop already has a record* for a vehicle with that
registration — a search over a collection, not a comparison of two objects in hand. `equals()`
cannot answer it because you do not have a second `Vehicle` to compare with; you have a
registration and a need to look.

It belongs on the repository — `findByRegistration(RegistrationNumber $reg): ?Vehicle` — which is
Lesson 3.1. The distinction is worth holding: *identity* is a property of the object, *lookup* is a
capability of the collection, and conflating them is how `Vehicle::findByRegistration()` static
methods appear and drag the database into the domain.

**Q18** It is unbounded state on an entity, and it is not needed for anything the class currently
does. Every reading appends forever, so a fleet vehicle in weekly for ten years carries five hundred
objects that are loaded on every read. In Module 3 that becomes a real cost: the mapper must
reconstitute all of them, or the entity becomes partially loaded, which is worse.

The stronger version of the argument: readings over time are *history*, and history is usually a
different concern from current state — often a separate read model or an event log, queried when
somebody asks rather than carried on the object always. The reference implementation says out loud
that this is something to disagree with, and this is the disagreement.

**Q19** The reading is refused. The service adviser does not read the exception; they see a form
error and they still need the job card open, so they enter 999,999 — or 240,000, on the assumption
it is a typo. The truck's service history is now wrong, permanently, in a way that will be believed
by everyone who reads it afterwards. Nobody logs a bug, because from the desk it looked like
validation working.

What should have been different: the guard should have been recognised as a sanity check and given
one of the two honest shapes — a bound high enough that no real vehicle reaches it, or a bound with
a documented override that records who overrode it and why. A sanity check with no override path has
become a business rule by accident, and it is the accident Lesson 1.4 is about.

**Q20** It is safe because PHP copies arrays on assignment, so the caller receives its own array and
appending to it does not touch the entity's. The `OdometerReading` objects inside are shared rather
than copied — and that is fine *precisely because they are immutable*. There is nothing a caller can
do to one that the entity would notice.

The condition under which the same code is a hole: **if the contents were mutable.** If the array
held entities, or value objects with setters, the caller would get references to the entity's own
internal objects and could change them from outside, bypassing every guard in the class. The array
copy protects the collection's shape and nothing about its contents. Module 2 returns to this at
length, because a job card's line items are exactly that case.
